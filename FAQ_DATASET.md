# TodaGo FAQ dataset and sources

The chatbot now uses **100 entries** with online references. The collection
adapts public Angkas, Grab, and Uber FAQ/help topics and BSP, GCash, PayMongo,
and Google guidance to TodaGo. The previous 33 project-authored entries were
reviewed against external counterparts and 67 additional topics were added.
There are 99 operational guidance entries and one dataset-provenance entry.

Deliverables generated by `npm run faq:sync`:

- [APA 7 bibliography and methodology wording](docs/FAQ_REFERENCES_APA.md)
- [All 100 FAQs mapped to online sources](docs/FAQ_SOURCE_MAP.md)
- [CSV dataset with answers, source URLs, and citations](docs/faq_dataset.csv)
- [Online source catalog](src/data/faq_online_sources.json)

## Where the answers come from

Online collections were reviewed on **19 November 2026**. Relevant topics
were selected, paraphrased, deduplicated, assigned to roles, and rewritten
for TodaGo. The rewritten instructions were checked against this workspace's
**Flutter screens, backend rules, and setup documentation**. Collection and
adaptation were AI-assisted; no faculty/domain-expert validation or passenger
survey has been performed. This describes the local implementation, not the
version currently deployed on a server or installed on a phone.

Every entry has `onlineReferences` identifying the source ID, the topic used,
and its relationship (`topic_adaptation`, `general_guidance`, or `methodology`).
The separate catalog records the direct URL, publisher/author, document title,
access date, and scope. APA citations use `n.d.` for undated web pages and
title-ordered suffixes for works sharing an author/date. Research papers are
marked as methodology references, not sources of ride instructions.

Every entry also has a `sources` list with a repository-relative `path` and a
`locator` (a function, class, UI label, or distinctive text). Its `reviewedAt`
field records when that answer was checked. The references identify the
implementation behind a TodaGo instruction. External links establish the
topic/guidance origin. Another provider's fees, refund deadlines, contacts,
insurance, vehicle requirements, or payment rules are not TodaGo policy.
The texts are rewritten; full external pages and benchmark records are not
redistributed. Some Grab articles require JavaScript, and their indexed
Help Centre content was reviewed.

This is a **source-linked reference knowledge base**, not a dataset used to train a model.
FAQ answers are selected locally by a deterministic matcher. Neither Flutter's
FAQ lookup nor `POST /api/ai/chat` calls an external language model. The
separate `/ride-intent` feature can call Gemini; it does not supply these FAQ
answers. No MFAQ/FAQIR benchmark records were imported. Those datasets must not
be described as the source of these 100 records. No passenger conversations, personal trip records, wallet balances,
payment receipts, or production database exports were used to create this set.

Map information is separate: `map_service.dart` uses Google Places with a
Photon fallback for place search, and Google directions with OSRM routing
fallbacks. The FAQ does not contain a live map dataset. The separate
`docs/panabo_eta_dataset.csv` is not used by the FAQ matcher.

## Where the data lives

- **Edit this canonical file:** `src/data/faqs.json` in the backend project.
- **Backend reader and matcher:** `src/services/faq.js`.
- **Online catalog and APA resolver:** `src/data/faq_online_sources.json`,
  `src/services/faqReferences.js`.
- **Flutter generated copy:** `todago_flutter/lib/data/faq_dataset.g.dart`.
- **Flutter reader and matcher:** `todago_flutter/lib/faq_service.dart`.

The generated copy lets FAQ answers work without a network request. It is
generated from the JSON, including its source metadata and review dates, so
there is only one content file to maintain. Rebuild the app to distribute a
new bundled dataset; deploy the backend to update its API answers. There is
no automatic remote FAQ update in this change.

The top-level JSON records a schema version, dataset version, provenance,
role-specific quick questions, and entries. Each entry contains:

- `id`, `category`, `question`, and `answer`;
- `aliases` for common English, Filipino, or Cebuano phrasings;
- `keywords` for complete-word or complete-phrase matching;
- `roles` (`passenger`, `driver`, and/or `guest`);
- `sources`, `onlineReferences`, and `reviewedAt`;
- optional `intentGroups` that require multiple concepts for specific issues.

The local-language aliases cover selected queries. Answers remain in English;
this is not complete translation or general natural-language understanding.

## How matching works

Exact questions and aliases take priority. Otherwise, complete keyword phrases
are scored by length. A longer, specific phrase can distinguish a missing
top-up from general top-up instructions. Partial words do not match: `rate`
cannot match `accurate`. Specific concept groups also match issues with filler
words, such as “my top-up money is missing.” Explicit place requests still
require a contiguous FAQ phrase to override directions. Equal scores and unsupported questions return a
clarification prompt. Only entries for the viewer's role are considered;
`commuter` maps to `passenger`, and unknown roles use the guest set.

All roles have a **Where do the FAQ answers come from?** quick question. The
API preserves `text` and `content`, and also returns `datasetVersion` and a
`faq` object containing the matched ID, category, review date, local sources,
and resolved online references with URLs and APA citations. Chat answers have
a **Sources** button opening the attributed online links.
`faq` is `null` for fallback answers. API authentication remains required.

FAQ answers explain workflows. They cannot confirm a payment, quote a live
fare, inspect a private account, determine a driver's current position, or
remove restrictions. Users must check the corresponding app screen for live
state. Unsupported refund rules or support contact details are not invented.

## Updating and checking the dataset

1. Read a relevant online FAQ/help source and check the corresponding current
   TodaGo screen and backend rule. Retain the external topic, not a conflicting
   provider policy. Add the source to `src/data/faq_online_sources.json` with
   its actual title, author, date if available, URL, access date, and scope.
2. Edit `src/data/faqs.json`. Add the online source ID and topic plus precise source paths and locators, update the
   entry's `reviewedAt`, and update the dataset version when publishing a revision.
3. Add useful aliases and phrases. Avoid broad keywords such as `ride`, `trip`,
   or `driver` that match many unrelated questions.
4. From `todago_backend`, run:

   ```sh
   npm run faq:sync
   npm run faq:check
   node --test test/faq.test.js
   ```

5. From `todago_flutter`, run:

   ```sh
   flutter test --no-pub test/faq_service_test.dart test/faq_chat_test.dart test/route_options_test.dart test/ride_entry_controls_test.dart
   flutter analyze --no-pub lib/faq_service.dart lib/ai_chat_screen.dart lib/location_query.dart test/faq_service_test.dart test/faq_chat_test.dart
   ```

Keep both project directories beside each other for the default sync target.
For separate checkouts, use `node scripts/sync-faqs.js --target <path-to-flutter>/lib/data/faq_dataset.g.dart`.
The sync also regenerates the APA bibliography, source map, and CSV; `--check`
checks those artifacts too. Commit both canonical JSON files and the generated
Flutter/documentation artifacts together. The checks
cover question/alias retrieval, role separation, ambiguity, representative
local-language phrases, source references, API compatibility, and copy parity.
Online URL structure and attribution are checked locally; the tests do not
prove a publisher's site will remain available or perform live payment actions.
These are curated retrieval checks, not a measured accuracy score on real
passenger traffic. Future additions should use reviewed, anonymized support
themes and an independently maintained evaluation set.
